1. ELEVATOR PITCH PL + EN

1.1 Elevator Pitch PL - 30 sekund

CoreLabTech to aplikacja Flask/PostgreSQL do analizy danych fizjologicznych

z sesji badawczych. System importuje pliki FIT z urzadzen sportowych oraz CSV

z pulsoksymetru, zapisuje metadane importu, synchronizuje dane po timestampach,

generuje wspolna os czasu, a nastepnie uruchamia analize regułowa/AI i zapisuje

wyniki do dashboardu oraz raportow.

1.2 Elevator Pitch PL - 2 minuty

CoreLabTech jest platforma researchowa do pracy z danymi fizjologicznymi.

Projekt rozwiazuje problem laczenia danych z roznych zrodel, ktore maja inne

formaty, inna czestotliwosc probkowania i inne timestampy. Uzytkownik moze

wgrac plik FIT, np. z Garmina, oraz CSV, np. z pulsoksymetru Checkme O2.

System najpierw wykonuje etap importu: parsuje pliki, waliduje rekordy, liczy

SHA-256, wykrywa duplikaty i zapisuje metadane w tabelach fit_imports oraz

csv_imports. Surowe rekordy trafiaja do fit_data i csv_data.

Nastepnie merge engine laczy dane po najblizszym timestampie. Wynik trafia do

merged_data razem z informacja, czy rekord zostal zsynchronizowany i jaka byla

roznica czasu delta_ms. Na koncu analysis_service analizuje zsynchronizowane

rekordy, liczy cechy, wykrywa potencjalne anomalie i zapisuje wynik do

ai_results.

Najwiekszym wyzwaniem bylo uporzadkowanie architektury: oddzielenie Flask routes

od SQL i logiki biznesowej. Docelowo routes sa cienkimi kontrolerami, services

trzymaja przypadki uzycia, repositories komunikuja sie z PostgreSQL, a migrations

utrzymuja schemat bazy.

1.3 Elevator Pitch EN - 30 seconds

CoreLabTech is a Flask/PostgreSQL research platform for physiological data

analysis. It imports FIT and CSV files, validates and stores raw measurements,

synchronizes signals by timestamp, builds a merged timeline, runs a rule-based

AI analysis, and exposes the results through APIs, dashboards, and reports.

1.4 Elevator Pitch EN - 2 minutes

CoreLabTech is a research-oriented platform for processing physiological session

data. The main challenge is combining signals coming from different devices and

formats, such as Garmin FIT files and pulse oximeter CSV files.

The system first performs data ingestion: it parses the uploaded files, validates

records, computes a SHA-256 hash, detects duplicate imports, stores import

metadata in fit_imports and csv_imports, and saves raw measurements into fit_data

and csv_data.

Then the merge engine synchronizes both timelines using nearest timestamp

matching. The merged output is stored in merged_data together with data quality

information such as synchronized and delta_ms. Finally, analysis_service computes

features, detects potential anomalies, and stores the result in ai_results.

The most important architectural improvement is separation of concerns:

Flask routes handle HTTP only, services implement business use cases,

repositories own SQL, and migrations define the PostgreSQL schema.

Pytanie:

Dlaczego hash pliku jest liczony przed zapisem?

Odpowiedz:

Hash SHA-256 pozwala wykryc, czy ten sam plik byl juz importowany dla tej samej

sesji. Jest stabilniejszy niz nazwa pliku, bo nazwe mozna zmienic, a zawartosc

pozostaje taka sama.

Pytanie:

Dlaczego import zapisuje metadane w csv_imports/fit_imports?

Odpowiedz:

Dzieki temu wiadomo, jaki plik zostal zaimportowany, ile rekordow sparsowano,

ile zapisano, jaki byl status i jaki parser zostal uzyty.

Pytanie:

Co oznacza DuplicateImportError?

Odpowiedz:

To wyjatek biznesowy informujacy, ze plik o tym samym hash zostal juz

zaimportowany dla danej sesji.

Dlaczego merge_asof?

Odpowiedz:

Bo dane FIT i CSV nie musza miec identycznych timestampow. merge_asof pozwala

Odpowiedz:

To maksymalna roznica czasu pomiedzy rekordami, ktore mozna uznac za

zsynchronizowane.

13. SOLID

13.1 Single Responsibility Principle

Kazdy modul ma jedna glowna odpowiedzialnosc.

Przyklad:

research_routes.py nie powinien miec SQL.

13.2 Open/Closed Principle

Kod powinien byc otwarty na rozszerzenie, zamkniety na modyfikacje.

Przyklad:

Mozna dodac nowy parser przez osobny modul, bez zmieniania calego pipeline'u.

13.3 Liskov Substitution Principle

Jesli parsery mialyby wspolny interfejs, kazdy parser powinien dac sie podmienic

bez psucia data_ingestion.

13.4 Interface Segregation Principle

Lepiej miec male funkcje repozytoriow niz jeden ogromny interfejs DB.

13.5 Dependency Inversion Principle

W idealnej wersji services zalezy od abstrakcji repozytoriow, a nie bezposrednio

od implementacji. W obecnym projekcie jest prostszy wariant proceduralny.

15. NAJTRUDNIEJSZE PYTANIA SENIOR

15.1 Dlaczego Repository?

Odpowiedz PL:

Repository izoluje SQL od logiki biznesowej i HTTP. Dzieki temu zmiana zapytan

nie wymaga zmian w routes, a serwisy mozna testowac przez mock repozytorium.

Answer EN:

Repository isolates SQL from business logic and HTTP controllers. It makes the

system easier to test, maintain, and refactor.

15.2 Dlaczego Service Layer?

Odpowiedz PL:

Service Layer trzyma przypadki uzycia. Route nie powinien wiedziec, jakie

zapytania trzeba wykonac i w jakiej kolejnosci. Service orkiestruje parsery,

repozytoria i transakcje.

Answer EN:

The service layer owns use cases. Routes should not know the sequence of SQL

operations. Services orchestrate parsers, repositories, validation, and

transactions.

15.3 Jak skalowac?

Odpowiedz PL:

Najpierw profilowalbym bottlenecki. Importy mozna przeniesc do background jobs,

bulk inserty juz pomagaja przy wydajnosci. Merge i analiza moga isc do kolejki.

PostgreSQL mozna indeksowac po session_id, import_id i timestamp.

Answer EN:

I would start with profiling. Imports can be moved to background jobs, bulk

inserts already improve throughput, merge and analysis can run asynchronously,

and PostgreSQL should be indexed by session_id, import_id, and timestamp.

15.4 Czy uzyc RabbitMQ?

Odpowiedz PL:

Tak, jesli import, merge albo analiza trwaja dlugo i nie powinny blokowac HTTP.

Wtedy request tworzy job, worker przetwarza zadanie, a frontend odpytuje status.

Answer EN:

Yes, if imports, merges, or analysis become long-running tasks. HTTP should

create a job, a worker should process it, and the frontend can poll job status.

15.5 Czy robic mikroserwisy?

Odpowiedz PL:

Nie od razu. Najpierw modularny monolit: routes, services, repositories. Gdy

granice domeny i obciazenie beda jasne, mozna wydzielic worker importow,

analysis service albo reporting service.

Answer EN:

Not immediately. I would start with a modular monolith. Once domain boundaries

and scaling needs are clear, imports, analysis, or reporting can be extracted.

15.6 Jak zapewnic idempotencje?

Odpowiedz PL:

Przy imporcie przez UNIQUE(session_id, file_hash). Przy jobach przez statusy

i identyfikatory importow. Operacja powtorzona nie powinna tworzyc duplikatow.

Answer EN:

For imports, by using UNIQUE(session_id, file_hash). For jobs, by tracking

statuses and import identifiers. Retrying should not create duplicates.

16. ODPOWIEDZI PL + EN

Pytanie:

What is the most important architectural decision in this project?

Odpowiedz PL:

Najwazniejsza decyzja to oddzielenie Flask routes od logiki biznesowej i SQL.

To zmienia projekt z duzego kontrolera w modularny backend.

Answer EN:

The most important architectural decision is separating Flask routes from

business logic and SQL. It turns the project from a large controller into a

modular backend.

Pytanie:

How do you prevent duplicate imports?

Odpowiedz PL:

Liczymy SHA-256 pliku i zapisujemy go z session_id. Constraint UNIQUE blokuje

ponowny import tego samego pliku dla tej samej sesji.

Answer EN:

We compute a SHA-256 file hash and store it with session_id. A UNIQUE constraint

prevents importing the same file twice for the same session.

Pytanie:

How does the merge engine work?

Odpowiedz PL:

Pobiera najnowszy completed FIT i CSV import, sortuje rekordy po timestampach

i laczy je algorytmem nearest timestamp w zadanej tolerancji.

Answer EN:

It loads the latest completed FIT and CSV imports, sorts records by timestamp,

and matches them using nearest timestamp matching within a configured tolerance.

21.9 PostgreSQL and SQL

Q: Why did you choose PostgreSQL?

A: PostgreSQL supports relational integrity, foreign keys, indexes, JSONB,

transactions, and better production scalability than SQLite.

Q: What is a primary key?

A: A primary key uniquely identifies each row in a table. For example,

csv_imports.id identifies a CSV import.

Q: What is a foreign key?

A: A foreign key enforces a relationship between tables. For example,

merged_data.merge_id references merge_jobs.merge_id.

Example:

FOREIGN KEY (merge_id)

REFERENCES merge_jobs(merge_id)

ON DELETE CASCADE

Q: Why do you use UNIQUE(session_id, file_hash)?

A: It prevents importing the same file twice for the same session.

Example:

CONSTRAINT uq_csv_import_session_hash

UNIQUE(session_id, file_hash)

Q: Why do you use indexes?

A: Indexes speed up queries commonly filtered by session_id, import_id, status,

or timestamp.

Example:

CREATE INDEX IF NOT EXISTS idx_merged_data_session_timestamp

ON merged_data(session_id, timestamp)

Q: What is a transaction?

A: A transaction groups database operations so they either all succeed or all

fail. CoreLabTech uses commit() after successful imports and rollback() on

errors.

Q: Why use execute_values()?

A: execute_values() performs bulk inserts efficiently, which is important when

importing many telemetry records from FIT or CSV files.

Example:

execute_values(cursor, "INSERT INTO fit_data (...) VALUES %s", values)

Q: Why use RETURNING id?

A: RETURNING lets PostgreSQL return the id of a newly inserted row without a

separate SELECT query.

Example:

INSERT INTO fit_imports (...)

VALUES (...)

RETURNING id

21.10 Application Architecture

Q: Why did you split the application into routes, services, and repositories?

A: This follows separation of concerns. Routes handle HTTP, services handle

business use cases, and repositories handle SQL. It makes the system easier to

test, maintain, and extend.

Example:

research_routes.py -> data_ingestion.py -> data_repository.py -> PostgreSQL

Q: Why should research_routes.py not execute SQL directly?

A: Because routes should not mix HTTP logic with persistence logic. Keeping SQL

in repositories supports the Single Responsibility Principle.

Q: What does the service layer do?

A: The service layer orchestrates a use case. For example, data_ingestion

validates a file, parses it, computes a hash, creates an import record, inserts

measurements, and commits the transaction.

21.11 ETL

Q: Why is CoreLabTech an ETL project?

A: It extracts data from FIT and CSV files, transforms it through parsing,

PostgreSQL tables.

Example:

Extract: uploaded FIT/CSV file

Transform: parse, validate, normalize, merge

Load: fit_data, csv_data, merged_data, ai_results

Q: What is Extract in this project?

A: Extract is reading uploaded FIT and CSV files from the request and parsing

their contents.

Q: What is Transform?

A: Transform includes timestamp parsing, column normalization, value validation,

nearest timestamp merge, and feature engineering.

Q: What is Load?

A: Load means writing records into PostgreSQL tables such as csv_imports,

fit_imports, csv_data, fit_data, merged_data, and ai_results.

21.12 Data Parsing and Pandas

Q: Why do you use pandas for CSV parsing?

A: pandas is reliable for tabular data. It handles CSV loading, column

normalization, missing values, and datetime conversion.

Example:

df = pd.read_csv(path, encoding="utf-8-sig")

df.columns = [normalize_column(column) for column in df.columns]

Q: What does pd.to_datetime() do?

A: It converts strings or other timestamp-like values into datetime objects.

This is required before merging time series.

Example:

timestamp = pd.to_datetime(raw_timestamp, errors="coerce")

Q: Why do you normalize column names?

A: Different CSV exports may use different spellings, spacing, or casing.

Normalization makes column matching predictable.

Example:

def normalize_column(name: Any) -> str:

return str(name).strip().lower().replace(" ", "_")

Q: Why do you use safe_float() and safe_int()?

A: Uploaded files may contain empty or invalid values. Safe conversion prevents

21.13 Merge Engine

Q: Why do you need a merge engine?

A: Garmin FIT and pulse oximeter CSV files are independent data sources. They

must be synchronized into one timeline before analysis can compare HR, HRV,

SpO2, and pulse.

Q: Why is timestamp the main merge key?

A: Physiological signals are time series. Timestamp is the natural axis that

allows measurements from different devices to be aligned.

Q: What is nearest timestamp matching?

A: It means finding the closest measurement in time from another data source,

within a configured tolerance.

Q: Why use tolerance_ms?

A: Tolerance prevents bad matches. If two records are too far apart in time, they

should not be treated as synchronized.

Example:

pd.merge_asof(

csv_for_merge,

fit_for_merge,

left_on="csv_timestamp",

right_on="fit_timestamp",

direction="nearest",

tolerance=pd.Timedelta(milliseconds=tolerance_ms),

)

Q: What happens when records cannot be matched?

A: They are marked as not synchronized or excluded from synchronized analysis.

This preserves data quality.

21.14 AI and Feature Engineering

Q: Is the current AI module machine learning?

A: Not yet. The current implementation is rule-based analysis with feature

engineering. It is designed so a machine learning model can be added later.

Q: Why did you start with rule-based AI?

A: Rule-based analysis is transparent and easier to validate. For medical or

research-inspired data, explainability is important before introducing a black

box model.

Q: What features do you calculate?

A: The system calculates features such as min SpO2, average HRV, max heart rate,

heart-rate-to-pulse difference, and match rate.

Example:

features = {

"min_spo2": min_spo2,

"avg_hrv": avg_hrv,

"max_heart_rate": max_hr,

"match_rate": match_rate,

}

Q: Why does AI run on merged_data instead of raw FIT and CSV separately?

A: Because the analysis compares signals from both sources. This comparison is

only meaningful after time synchronization.

Q: Why store AI results in ai_results?

A: Persisting results avoids recalculating them on every dashboard request and

creates an audit trail of model version, features, scores, and recommendations.

21.15 Repository Pattern

Q: Why did you use the Repository Pattern?

A: The Repository Pattern separates SQL from business logic. Services call

repository functions instead of embedding SQL directly.

Example:

import_id = create_csv_import(cursor, ...)

records_saved = insert_csv_measurements(cursor, ...)

Q: Why pass cursor as a parameter?

A: Passing cursor allows the service to control the transaction across multiple

repository calls. All database operations can commit or roll back together.

Q: What would be worse about putting SQL in services?

A: Services would become harder to read and test. SQL details would be mixed

with business workflow.

21.16 Dependency Injection

Q: Do you use dependency injection?

A: The project uses a simple manual form. Services call repository functions and

Example:

)

Q: Why is dependency direction important?

A: Routes should depend on services, services should depend on repositories,

and repositories should depend on the database. The direction should not be

reversed.

21.17 SOLID

Q: How does the project follow SRP?

A: Each layer has one main responsibility. Routes handle HTTP, services handle

business workflows, repositories handle SQL, and migrations handle schema.

Q: How does the project support Open/Closed?

A: New parsers, merge strategies, or analysis models can be added as new modules

without rewriting the entire route layer.

Q: How would Dependency Inversion improve the project?

A: Services could depend on repository interfaces instead of concrete functions,

21.30 Domain Knowledge

Pytanie:

Dlaczego logika importu jest w import_csv_file(), a nie bezposrednio w route?

Odpowiedz:

Czym sa argumenty domyslne?

Jaka jest roznica miedzy funkcja a klasa?

Odpowiedz:

Funkcja wykonuje konkretne zachowanie, a klasa grupuje dane i zachowanie. W

Pytanie:

Co robi @dataclass?

Odpowiedz:

@dataclass automatycznie generuje metody takie jak __init__ i __repr__. W

22.1 What exists in the project

Q: What is the goal of the Playwright framework in CoreLabTech?

A: The goal is to validate the most important user workflows end-to-end:

authentication, chamber session flow, CSV/FIT upload, merge, AI analysis,

dashboard validation, and API contract checks. It is not just clicking through

screens; it verifies the business pipeline.

Example answer:

"I built the Playwright layer around business workflows, not isolated selectors.

The tests should prove that a researcher can log in, run a chamber session,

upload data, execute merge, run AI analysis, and see valid results."

22.2 Framework structure

Recommended structure:

Q: Why separate tests/e2e from tests/pom?

A: tests/e2e contains scenarios and assertions. tests/pom contains reusable page

objects. This separation keeps tests readable and avoids duplicating locators

and UI actions across multiple specs.

Example:

const dashboard = new DashboardPage(page);

await dashboard.open();

await dashboard.uploadCsv("sample.csv");

await dashboard.runMerge();

22.3 Page Object Model

Q: What is Page Object Model?

A: Page Object Model is a pattern where each important page or area of the app

is represented by a class. The class exposes meaningful methods instead of raw

selectors in every test.

Example:

export class DashboardPage {

constructor(private page: Page) {}

async open() {

await this.page.goto("/research");

}

async runMerge() {

await this.page.getByRole("button", { name: "Run Merge" }).click();

}

}

Q: Why is POM useful in CoreLabTech?

A: The dashboard and chamber flow can change visually, but the business actions

remain similar. POM isolates selector changes in one file instead of forcing

updates in every spec.

22.4 Fixtures and auth setup

Q: Why use auth.setup.ts?

A: Authentication setup can log in once and store browser state. Tests can reuse

that authenticated state instead of repeating login in every test.

Example:

// auth.setup.ts

await page.goto("/login");

await page.fill("#email", process.env.TEST_EMAIL!);

await page.fill("#password", process.env.TEST_PASSWORD!);

await page.click("button[type='submit']");

await page.context().storageState({ path: "playwright/.auth/user.json" });

Q: Why is this important?

A: It makes tests faster and less flaky because the login flow is not repeated

unnecessarily.

22.5 Locators

Q: Which locators are preferred?

A: Prefer user-facing locators such as getByRole, getByLabel, getByText, and

stable test ids. Avoid brittle CSS chains when possible.

Example:

await page.getByRole("button", { name: "Run Playwright QA" }).click();

await expect(page.locator("h1")).toContainText("HBOT Testing Session");

Q: How would you reduce flaky selectors?

A: Use accessible roles, stable labels, explicit test ids for complex widgets,

and avoid selectors based on layout or deeply nested CSS.

22.6 API contract tests

Q: Why does CoreLabTech need API contract tests?

A: The frontend depends on stable JSON responses from endpoints such as

/api/run_analysis, /api/merged_data/<session_id>, and /api/analysis/latest.

Contract tests catch accidental response shape changes.

Example:

const response = await request.post("/api/run_analysis", {

data: { session_id: "S001" },

});

expect(response.status()).toBe(201);

const body = await response.json();

expect(body).toHaveProperty("analysis_id");

expect(body).toHaveProperty("merge_id");

expect(body).toHaveProperty("overall_score");

22.8 Senior interview questions - Playwright

Q: How did you design the Playwright framework?

A: I separated tests from page objects. Specs describe business scenarios, while

POM classes hide locators and repeated actions. I also use auth setup, helper

functions, API checks, and clear assertions around the research pipeline.

Q: How would you handle flaky tests?

A: I would use stable locators, wait for visible business states instead of

timeouts, isolate test data, avoid shared mutable state, and keep retries as a

last safety net rather than a fix for bad synchronization.

Q: What would you put in CI?

A: Smoke tests on every pull request, full E2E on main branch or nightly,

artifacts such as screenshots/videos/traces on failure, and contract tests for

critical API endpoints.

Q: How do Playwright tests support the project architecture?

A: They verify that the layers work together from the user's perspective:

Frontend -> Flask routes -> services -> repositories -> PostgreSQL -> AI result.

22.11 Design principles for a good Playwright framework

1. Testuj zachowanie, nie implementacje UI.

2. Uzywaj getByRole/getByLabel/getByText zamiast kruchych CSS.

3. POM ma chowac selektory, ale nie moze byc drugim frameworkiem UI.

4. Dane testowe musza byc izolowane i deterministyczne.

5. Nie uzywaj waitForTimeout jako normalnego mechanizmu synchronizacji.

6. Asercje powinny czekac na stan biznesowy, np. "PRE SAVED".

7. API contract tests powinny lapac HTML/non-JSON regresje.

8. Trace/video/screenshot powinny byc wlaczone na failure.

9. Testy smoke maja byc szybkie i stabilne.

10. Full E2E moze byc wolniejsze, ale musi pokrywac krytyczny pipeline.

23.4 Example Gatling simulation

Q: How would you write a Gatling test for run_analysis?

A: I would send POST requests with JSON payloads to /api/run_analysis and check

that the response status is successful and contains expected fields.

Example:

class RunAnalysisSimulation extends BaseSimulation {

val scn = scenario("Run AI Analysis")

.exec(

http("POST /api/run_analysis")

.post("/api/run_analysis")

.header("Content-Type", "application/json")

.body(StringBody("""{"session_id":"S001"}""")).asJson

.check(status.in(200, 201))

.check(jsonPath("$.analysis_id").exists)

.check(jsonPath("$.merge_id").exists)

)

setUp(

scn.inject(rampUsers(20).during(60))

).protocols(httpProtocol)

}

23.5 Performance metrics

Q: Which Gatling metrics matter most?

A: The most important metrics are response time percentiles, request count,

success/failure count, requests per second, and error rate.

Important metrics:

p50 response time

p95 response time

p99 response time

max response time

requests per second

failed requests

status code distribution

Q: Why are p95 and p99 more useful than average?

A: Average can hide slow requests. p95 and p99 show the experience of slower

users and reveal tail latency.

23.6 Performance thresholds

Example targets for CoreLabTech:

GET /api/sessions:

p95 < 300 ms

POST /upload_csv:

p95 < 3000 ms for small files

POST /upload_fit:

p95 < 5000 ms for small/medium files

POST /api/during_merge:

p95 < 5000 ms for typical sessions

POST /api/run_analysis:

p95 < 2000 ms after merge is ready

Error rate:

< 1%

Q: Should thresholds be fixed forever?

A: No. Thresholds should be based on expected file sizes, hardware, database

capacity, and business requirements. They should be reviewed after measuring

real usage.

23.7 services/performance_service.py

Q: What is the role of performance_service.py?

A: It acts as a Python wrapper around Gatling. It selects the simulation,

executes Maven/Gatling, parses stdout, saves latest.json and history.json, and

exposes results through Flask routes.

Example flow:

POST /api/performance/run

-> performance_routes.py

-> run_gatling_test(test_type)

-> mvn gatling:test

-> data/performance/latest.json

Q: Why store performance history?

A: History allows tracking whether performance improves or gets worse over time.

It can be used as a lightweight performance regression signal.

23.8 Gatling in CI/CD

Q: Would you run Gatling on every pull request?

A: I would run a small smoke performance test on pull requests and heavier load

tests nightly or before releases. Full load tests can be too expensive for every

commit.

Example CI strategy:

Pull request:

- compile

- unit tests

- API smoke tests

- tiny Gatling smoke test

Nightly:

- database setup

- E2E tests

- full Gatling scenarios

- performance trend report

23.9 Senior interview questions - Gatling

Q: Why did you add performance tests?

A: The project has heavy operations: parsing uploaded files, bulk inserting

measurements, merging time series, and running analysis. Performance tests show

whether these operations remain acceptable under realistic load.

Q: What would you monitor during a Gatling run?

A: I would monitor Gatling metrics, Flask logs, PostgreSQL CPU/IO, slow queries,

connection count, memory usage, and error responses.

Q: What bottlenecks do you expect?

A: Large file parsing, database bulk inserts, timestamp merge for large

sessions, missing indexes, and synchronous report generation could become

bottlenecks.

Q: How would you optimize upload performance?

A: Use streaming or chunking for large files, keep execute_values bulk inserts,

add indexes carefully, validate file size early, and move long processing to a

background job queue.

Q: How would you optimize merge performance?

A: Ensure data is indexed by session_id and timestamp, merge only the relevant

latest imports, avoid repeated merge for the same imports, and cache/store

merged_data.

Q: What is the difference between load, stress, and endurance testing?

A: Load testing checks expected traffic. Stress testing pushes the system beyond

normal capacity. Endurance testing runs for a long time to detect leaks,

resource exhaustion, or performance degradation.

23.12 Types of performance tests

Load test:

Sprawdza zachowanie systemu przy oczekiwanym ruchu.

Przyklad:

80 uzytkownikow rampUsers dla GET /api/sessions.

Performance test:

Mierzy czas odpowiedzi, throughput i stabilnosc dla konkretnej operacji.

Przyklad:

POST /upload_csv z malym plikiem CSV i progiem p95 < 2000 ms.

Stress test:

Stopniowo przekracza normalny ruch, zeby znalezc punkt zalamania.

Przyklad:

Zwiekszac constantUsersPerSec dla /api/during_merge az p95 albo error rate

przekroczy prog akceptacji.

Endurance / soak test:

Uruchamia stabilny ruch przez dlugi czas, zeby wykryc memory leaks, degradacje

wydajnosci albo narastanie connection count.

Spike test:

Symuluje nagly skok ruchu.

Przyklad:

nagle 100 uzytkownikow wywoluje /api/sessions po wdrozeniu.

Scalability test:

Sprawdza, czy zwiekszenie zasobow albo liczby instancji poprawia throughput.

Volume test:

Sprawdza prace na duzej ilosci danych, np. bardzo duze tabele fit_data,

csv_data i merged_data.

23.17 Metrics and interpretation

Najwazniejsze metryki:

request_count,

min_ms,

max_ms,

mean_ms,

p50_ms,

p75_ms,

p95_ms,

p99_ms,

requests_per_sec,

failed_count,

status code distribution.

Interpretacja:

p50:

Mediana. Pokazuje typowy request.

p95:

95% requestow bylo szybszych niz ta wartosc. Bardzo wazne dla SLA/SLO.

p99:

Tail latency. Pokazuje najwolniejsze przypadki bez patrzenia tylko na max.

mean:

Srednia. Przydatna, ale moze ukrywac ogon opoznien.

max:

Najwolniejszy request. Moze byc outlierem, ale warto go sprawdzic.

failed_count:

Bledy HTTP, timeouty, nieudane checki.

requests_per_sec:

Throughput, czyli ile requestow system obsluguje na sekunde.

23.18 Bottleneck analysis

Jak analizowac bottleneck?

1. Sprawdz Gatling p95/p99 i error rate.

2. Sprawdz, ktory endpoint zwalnia.

3. Sprawdz logi Flask/Gunicorn.

4. Sprawdz PostgreSQL slow queries.

nie powtarzac merge dla tych samych importow,

profilowac Pandas merge_asof.

Sessions API wolne:

indeks na full_sessions.created_at i user_id,

paginacja,

ograniczenie kolumn,

cache dla dashboardu.

Analysis wolne:

liczyc features na merged_data z limitami,

przechowywac wynik w ai_results,

nie przeliczac bez potrzeby,

przeniesc dluzsza analize do kolejki.

Database bottleneck:

EXPLAIN ANALYZE,

indeksy,

connection pooling,

VACUUM/ANALYZE,

limitowanie duzych SELECTow.

24. SQL INTERVIEW Q&A FOR CORELABTECH

This section focuses on SQL questions that can appear in interviews. It uses

CoreLabTech tables and examples.

24.1 Basic SELECT

Q: How would you select all completed CSV imports for one session?

A: I would query csv_imports by session_id and status.

Example:

SELECT

id,

session_id,

filename,

records_saved,

imported_at

FROM csv_imports

WHERE session_id = 'S001'

AND status = 'completed'

ORDER BY imported_at DESC;

Q: Why use WHERE?

A: WHERE filters rows before returning them. Without WHERE, the query would scan

and return imports for all sessions.

24.2 ORDER BY and LIMIT

Q: How do you get the latest completed FIT import?

A: Use WHERE to filter completed imports, ORDER BY imported_at DESC and LIMIT 1.

Example:

SELECT

id,

session_id,

file_hash,

records_saved

FROM fit_imports

WHERE session_id = 'S001'

AND status = 'completed'

ORDER BY imported_at DESC, id DESC

LIMIT 1;

Q: Why order by imported_at and id?

A: imported_at orders by time, and id is a deterministic tie-breaker if two rows

have the same timestamp.

24.3 INSERT

Q: How is a CSV import inserted?

A: The repository inserts metadata into csv_imports and uses RETURNING id to get

the import id for csv_data rows.

Example:

INSERT INTO csv_imports (

session_id,

user_id,

filename,

file_hash,

records_parsed,

device,

parser_version,

status

)

VALUES (

'S001',

'U001',

'pulseox.csv',

'abc123',

120,

'Checkme O2',

'csv-v1',

'processing'

)

RETURNING id;

Q: Why not insert directly into csv_data only?

A: csv_imports stores metadata about the import. csv_data stores measurements.

Separating them makes duplicate detection, audit, and troubleshooting easier.

24.4 UPDATE

Q: How do you mark an import as completed?

A: Update records_saved, records_rejected, timestamps, and status.

Example:

UPDATE csv_imports

SET

records_saved = 118,

records_rejected = 2,

first_timestamp = '2026-07-18 10:00:00',

last_timestamp = '2026-07-18 10:02:00',

status = 'completed',

error_message = NULL

WHERE id = 10;

Q: Why update status after inserting measurements?

A: The import should only become completed after measurement rows are safely

written. Otherwise the database could show a completed import without data.

24.5 DELETE

Q: How do you delete completed sessions?

A: In the current service, delete_research_sessions deletes rows from

full_sessions by session_id. If deeper cleanup is required, related measurement

tables should be handled deliberately.

Example:

DELETE FROM full_sessions

WHERE session_id = ANY(ARRAY['S001', 'S002']);

Q: What is the risk of DELETE?

A: DELETE can permanently remove data. It should be restricted by role, filtered

carefully, and ideally protected by backups or soft-delete for sensitive data.

24.6 INNER JOIN

Q: How would you join merge_jobs with ai_results?

A: Use INNER JOIN when you only want merge jobs that already have AI results.

Example:

SELECT

mj.merge_id,

mj.session_id,

mj.merged_records,

ar.ai_result_id,

ar.overall_score,

ar.created_at

FROM merge_jobs mj

INNER JOIN ai_results ar

ON ar.merge_id = mj.merge_id

WHERE mj.session_id = 'S001'

ORDER BY ar.created_at DESC;

Q: What does INNER JOIN mean?

A: It returns only rows where both tables have matching records.

24.7 LEFT JOIN

Q: How would you find merge jobs without AI results?

A: Use LEFT JOIN and filter where ai_results is missing.

Example:

SELECT

mj.merge_id,

mj.session_id,

mj.status,

mj.finished_at

FROM merge_jobs mj

LEFT JOIN ai_results ar

ON ar.merge_id = mj.merge_id

WHERE ar.ai_result_id IS NULL

AND mj.status = 'COMPLETED';

Q: Why use LEFT JOIN here?

A: LEFT JOIN keeps all merge_jobs rows and attaches ai_results when available.

Rows with NULL ai_result_id represent completed merges without analysis.

24.8 GROUP BY

Q: How would you count imports per status?

A: Use GROUP BY status.

Example:

SELECT

status,

COUNT(*) AS import_count

FROM csv_imports

GROUP BY status

ORDER BY import_count DESC;

Q: How would you count samples per session?

A: Group measurement rows by session_id.

Example:

SELECT

session_id,

COUNT(*) AS samples

FROM merged_data

GROUP BY session_id

ORDER BY samples DESC;

Q: Why use GROUP BY?

A: GROUP BY aggregates rows into groups, which is useful for reports, metrics,

and dashboards.

24.9 Aggregate functions

Q: How would you calculate average SpO2 per session?

A: Use AVG(spo2) grouped by session_id.

Example:

SELECT

session_id,

ROUND(AVG(spo2)::numeric, 2) AS avg_spo2,

MIN(spo2) AS min_spo2,

MAX(spo2) AS max_spo2

FROM merged_data

WHERE synchronized = TRUE

GROUP BY session_id;

Q: Why filter synchronized = TRUE?

A: AI and analytics should use only records that were reliably matched between

FIT and CSV timelines.

24.10 HAVING

Q: How would you find sessions with more than 1000 merged samples?

A: Use GROUP BY and HAVING.

Example:

SELECT

session_id,

COUNT(*) AS merged_samples

FROM merged_data

GROUP BY session_id

HAVING COUNT(*) > 1000;

Q: What is the difference between WHERE and HAVING?

A: WHERE filters rows before aggregation. HAVING filters groups after

aggregation.

24.11 Constraints

Q: What constraints are important in CoreLabTech?

A: Primary keys identify rows, foreign keys enforce relationships, unique

constraints prevent duplicate imports, and check constraints can enforce allowed

statuses or numeric ranges.

Example CHECK:

ALTER TABLE csv_imports

ADD CONSTRAINT chk_csv_import_status

CHECK (status IN ('processing', 'completed', 'failed'));

Q: Why is UNIQUE(session_id, file_hash) better than UNIQUE(filename)?

A: Filename can change, but file content hash remains stable. The same file with

a different name should still be detected as a duplicate.

24.12 Indexes

Q: Which indexes are important in this project?

A: Indexes on session_id, import_id, status, timestamp, and merge_id are

important because most queries filter or order by those columns.

Example:

CREATE INDEX IF NOT EXISTS idx_fit_data_session_timestamp

ON fit_data(session_id, timestamp);

Q: Can too many indexes be bad?

A: Yes. Indexes speed up reads but slow down writes and consume storage. Since

CoreLabTech imports many rows, indexes should be added based on real query

patterns.

24.13 Transactions

Q: How does a transaction protect import consistency?

A: A transaction ensures that creating an import, inserting measurements, and

marking the import completed happen as one unit. If any step fails, rollback

removes partial changes.

Example:

try:

import_id = create_csv_import(cursor, ...)

insert_csv_measurements(cursor, import_id=import_id, ...)

complete_csv_import(cursor, import_id=import_id, ...)

connection.commit()

except Exception:

connection.rollback()

raise

Q: What could go wrong without transactions?

A: The system could store an import row without measurements, or measurements

without a completed import status.

24.14 JSONB

Q: Why use JSONB in ai_results?

A: AI features and raw result payloads may evolve over time. JSONB allows

storing flexible structured data while keeping relational columns for key

metrics.

Example:

SELECT

ai_result_id,

features_json ->> 'min_spo2' AS min_spo2

FROM ai_results

WHERE session_id = 'S001';

Q: When should you not use JSONB?

A: If a field is frequently filtered, joined, or constrained, it is often better

as a normal relational column.

24.15 Window functions

Q: How would you select the latest AI result per session?

A: Use ROW_NUMBER() partitioned by session_id.

Example:

SELECT *

FROM (

SELECT

ar.*,

ROW_NUMBER() OVER (

PARTITION BY session_id

ORDER BY created_at DESC, ai_result_id DESC

) AS rn

FROM ai_results ar

) ranked

WHERE rn = 1;

Q: Why use a window function instead of GROUP BY?

A: GROUP BY aggregates rows and loses row-level details. ROW_NUMBER keeps the

full row and ranks it within each session.

24.16 Query performance

Q: How would you investigate a slow query?

A: I would use EXPLAIN ANALYZE, check indexes, inspect row counts, verify filter

selectivity, and look for unnecessary full table scans.

Example:

EXPLAIN ANALYZE

SELECT *

FROM merged_data

WHERE session_id = 'S001'

ORDER BY timestamp;

Q: What query may become expensive in CoreLabTech?

A: Loading all fit_data or csv_data for a large session and merging it may become

expensive. Indexes on session_id and timestamp help, and large jobs may need

background processing.

24.17 SQL injection

Q: How does the project avoid SQL injection?

A: Repository queries use parameterized SQL with %s placeholders instead of

string formatting for user input.

Example:

cursor.execute(

"""

SELECT *

FROM csv_data

WHERE session_id = %s

""",

(session_id,),

)

Q: Is f-string SQL always unsafe?

A: It is unsafe for user input. In rare cases, controlled internal identifiers

can be used, but they must be validated against an allowlist. CoreLabTech does

this in count_rows() by checking table names against allowed_tables.

24.18 Practical SQL interview answers

Q: Explain the database design in CoreLabTech.

A: The database separates metadata from measurements. csv_imports and

fit_imports store file-level metadata, csv_data and fit_data store raw

measurements, merge_jobs stores merge process metadata, merged_data stores the

synchronized timeline, and ai_results stores analysis outputs.

Q: Why not keep everything in one table?

A: One table would mix different responsibilities and create duplication.

Separate tables improve data integrity, query performance, and auditability.

Q: How do you model one-to-many relationships?

A: One import has many measurement rows. The import table has id, and data tables

store import_id as a foreign key.

Q: How do you model the AI result relationship?

A: ai_results references merge_jobs through merge_id because the analysis is

based on a specific merged timeline.

Q: What would you improve in the database next?

A: I would add CHECK constraints for statuses, consider soft delete for sessions,

add migration tracking, and add more integration tests that create the schema

from scratch.

25. HTTP, AUTH, COOKIES, CORS

25.1 HTTP basics

Q: What is HTTP in the context of CoreLabTech?

A: HTTP is the protocol used by the frontend and API clients to communicate with

the Flask backend. CoreLabTech exposes endpoints for uploads, sessions, merge,

analysis, reports, and performance tests.

Example:

POST /upload_csv

GET /api/merged_data/S001

POST /api/run_analysis

GET /report/S001

Q: What is the difference between GET and POST?

A: GET retrieves data and should not change server state. POST creates or starts

an operation. CoreLabTech uses GET for reading analysis or merged data and POST

for uploads, merge, and analysis.

Q: What is multipart/form-data?

A: It is the content type used for file uploads. CoreLabTech uses it for FIT and

CSV uploads because the request contains both a file and form fields such as

session_id.

Example:

file = request.files.get("file")

session_id = request.form.get("session_id")

25.2 Headers and content types

Q: Why does content type matter?

A: The backend needs to know how to parse the request. JSON requests use

application/json, while file uploads use multipart/form-data.

Example:

Content-Type: application/json

Content-Type: multipart/form-data

Q: What response headers matter for file reports?

A: Content-Type and Content-Disposition matter. They tell the browser that the

response is a PDF attachment.

Example:

return send_file(

path,

as_attachment=True,

download_name=f"corelabtech_{session_id}_report.pdf",

)

25.3 Cookies and sessions

Q: How does login state work in Flask?

A: Flask-Login stores user session information in a secure session cookie. The

server uses it to identify the current_user for protected endpoints.

Q: Why set SESSION_COOKIE_HTTPONLY?

A: HttpOnly prevents JavaScript from reading the cookie, reducing the impact of

XSS attacks.

Q: What is SameSite?

A: SameSite controls whether cookies are sent with cross-site requests. It helps

reduce CSRF risk. A production configuration should explicitly set SameSite

based on deployment needs.

25.4 CORS

Q: What is CORS?

A: CORS controls whether browsers allow frontend code from one origin to call an

API on another origin.

Q: Why is CORS relevant?

A: If the dashboard is served from a different domain than the Flask API, CORS

must be configured carefully. Too broad CORS can expose the API unnecessarily.

25.5 Idempotency

Q: What is idempotency?

A: An operation is idempotent if repeating it has the same effect as running it

once.

Q: Is file upload idempotent in CoreLabTech?

A: It is partially idempotent through UNIQUE(session_id, file_hash). Uploading

the same file again results in duplicate detection instead of duplicated rows.

25.6 Standard API error shape

Q: Why should API errors have a consistent format?

A: Consistent errors are easier for frontend and tests to handle.

Example:

{

"status": "error",

"error": "missing session_id"

}

26. DEEP SECURITY Q&A

26.1 Password hashing

Q: Why store password_hash instead of password?

A: Passwords must never be stored in plain text. A hash protects users if the

database leaks.

Q: What would you improve?

A: Ensure strong hashing parameters, enforce password policy, add password reset

tokens with expiration, and audit admin account operations.

26.2 XSS

Q: What is XSS?

A: Cross-Site Scripting happens when attacker-controlled JavaScript is rendered

in a user's browser.

Q: Where could XSS appear in CoreLabTech?

A: Any UI rendering user-controlled fields such as email, session_id, filename,

or notes must escape values and avoid unsafe innerHTML.

26.3 CSRF flow

Q: How does CSRF protection work?

A: The server issues a token, the frontend sends it with state-changing

requests, and the server rejects requests without a valid token.

Q: Which endpoints need CSRF?

A: State-changing endpoints such as uploads, delete_sessions, save_phase,

save_full_session, merge, analysis, and account management.

26.4 RBAC vs ABAC

Q: What is RBAC?

A: Role-Based Access Control grants permissions based on roles such as admin,

researcher, operator, and viewer.

Q: What is ABAC?

A: Attribute-Based Access Control uses attributes such as owner, department,

session status, or data sensitivity. CoreLabTech currently uses RBAC, but ABAC

could restrict users to their own sessions.

26.5 Secrets management

Q: Where should DATABASE_URL and SECRET_KEY be stored?

A: In environment variables or a secret manager, not in source code.

Q: What is the risk of committing secrets?

A: Anyone with repository access could connect to production systems or forge

sessions.

27. TEST STRATEGY AND QA ARCHITECTURE

27.1 Test pyramid

Q: What is the test pyramid?

A: It is a testing strategy with many unit tests, fewer integration tests, and

even fewer E2E tests. This keeps feedback fast and reliable.

CoreLabTech example:

Unit: csv_parser, fit_parser, analysis feature calculations

Integration: data_ingestion + PostgreSQL

API: upload, merge, analysis endpoints

E2E: Playwright dashboard workflow

Performance: Gatling upload/merge/analysis

27.2 Risk-based testing

Q: Which areas are highest risk?

A: File upload, parser correctness, database transactions, merge accuracy,

analysis output, permissions, and report generation.

Q: How would you prioritize tests?

A: I would test the pipeline first: upload CSV, upload FIT, merge, analysis, and

report. Then I would add negative cases and performance tests.

27.3 Test data management

Q: Why is test data important?

A: FIT and CSV parsing depends on realistic data. Tests need stable sample files

with known expected records and timestamps.

Q: How would you prepare test data?

A: Keep small deterministic CSV/FIT fixtures, create unique session_id values,

and clean up database rows after tests.

27.4 Mocking vs real database

Q: When would you mock?

A: For unit tests of service logic where database behavior is not the focus.

Q: When would you use a real database?

A: For repository and migration tests. SQL, constraints, transactions, and

foreign keys should be tested against PostgreSQL.

27.5 Quality gates

Q: What quality gates would you add to CI?

A: Python compile/lint, unit tests, migration setup on fresh PostgreSQL, API

tests, Playwright smoke tests, and a small Gatling performance smoke test.

28.3 Metrics

28.4 Prometheus

28.5 Alerts

29.4 Gunicorn

Q: Why not run Flask dev server in production?

A: The Flask dev server is for development. Production should use WSGI servers

such as Gunicorn behind a reverse proxy.

29.5 Deployment environments

Q: What environments would you define?

A: local, test, staging, and production. Each should have separate config,

database, secrets, and logging level.

29.6 Rolling and blue-green deployments

Q: What is a rolling deployment?

A: Instances are updated gradually, reducing downtime.

Q: What is blue-green deployment?

A: Two environments exist: blue is current production, green is new. Traffic is

switched after validation.

30. ADVANCED POSTGRESQL

30.1 Isolation levels

Q: What is transaction isolation?

A: Isolation controls how concurrent transactions see each other's changes.

PostgreSQL defaults to READ COMMITTED.

Q: Why does it matter?

A: Concurrent imports or analysis jobs could read or write overlapping data.

Isolation determines what each transaction can see.

30.2 Locks and deadlocks

Q: What is a deadlock?

A: A deadlock happens when two transactions wait for each other forever.

PostgreSQL detects deadlocks and aborts one transaction.

Q: How would you reduce deadlocks?

A: Keep transactions short, update tables in consistent order, and avoid long

locks during expensive processing.

30.3 Connection pooling

Q: Why use connection pooling?

A: Opening a new PostgreSQL connection per request is expensive. A pool reuses

connections and protects the database from too many concurrent connections.

30.4 Migration versioning

Q: What is missing from the current migration setup?

A: The project has runnable migration scripts, but not yet a migration version

table that records which migrations were applied.

Q: What would you add?

A: A schema_migrations table with migration name, checksum, applied_at, and

status.

30.5 Backup and restore

Q: Why is backup important?

A: Research data and imports may be hard to recreate. Backups protect against

human error, corruption, and failed deployments.

30.6 VACUUM and ANALYZE

Q: What do VACUUM and ANALYZE do?

A: VACUUM cleans dead tuples. ANALYZE updates planner statistics. Both help

PostgreSQL maintain performance.

31. DATA QUALITY AND DATA ENGINEERING

31.1 Data quality metrics

Q: What data quality metrics does CoreLabTech have?

A: records_parsed, records_saved, records_rejected, match_rate,

synchronized records, data_quality_score, and error_message.

31.2 Data lineage

Q: What is data lineage?

A: Data lineage tracks where data came from and how it was transformed.

CoreLabTech lineage:

file -> import row -> raw data -> merged_data -> ai_results -> report

31.3 Schema evolution

Q: What is schema evolution?

A: It is controlled change of database schema over time. Migrations should add

new columns or tables without breaking existing data.

31.4 Late-arriving data

Q: What if a CSV file arrives after FIT was already merged?

A: The system should either rerun merge for the latest completed imports or

track merge inputs so users know which import versions were used.

31.5 Idempotent ETL

Q: Why should ETL be idempotent?

A: If an import job is retried, it should not duplicate rows. CoreLabTech uses

file_hash plus session_id to detect duplicate imports.

32. SENIOR SYSTEM DESIGN Q&A

32.1 Modular monolith vs microservices

Q: Why keep CoreLabTech as a modular monolith?

A: A modular monolith is simpler to develop and deploy while still preserving

clear boundaries. Microservices should be introduced only when scaling,

ownership, or deployment needs justify the extra complexity.

32.2 Background jobs

Q: Which tasks should become background jobs?

A: Large file imports, merge, AI analysis, PDF generation, and performance test

execution are good candidates.

32.3 Eventual consistency

Q: What changes if jobs become asynchronous?

A: The API may return a job_id immediately, while the final result appears later.

The frontend must poll or subscribe to job status.

Example:

{

"status": "queued",

"job_id": "merge-S001-001"

}

32.4 Bounded contexts

Q: What bounded contexts can you identify?

A: Authentication, research sessions, data ingestion, merge, analysis, reports,

QA automation, and performance testing.

32.5 Scalability plan

Q: How would you scale CoreLabTech step by step?

A:

1. Add indexes and optimize SQL.

2. Add connection pooling.

3. Move long tasks to background workers.

4. Add job status tables.

5. Add observability.

6. Split services only when operationally necessary.

32.6 Trade-off question

Q: What trade-off did you make by using a simple migration runner?

A: It is easy to understand and run locally, but it lacks version tracking,

rollback management, checksums, and migration history. A production system should

use a stronger migration tool or add a schema_migrations table.

34.1 SQL - tlumaczenie PL

Pytanie:

Jak wybrac wszystkie zakonczone importy CSV dla jednej sesji?

Odpowiedz:

Uzylbym SELECT z filtrem WHERE po session_id i status = 'completed', a wynik

posortowalbym po imported_at malejaco.

Pytanie:

Jaka jest roznica miedzy WHERE i HAVING?

Odpowiedz:

WHERE filtruje pojedyncze rekordy przed agregacja. HAVING filtruje grupy po

GROUP BY, czyli po agregacji.

Pytanie:

Jak pobrac najnowszy zakonczony import FIT?

Odpowiedz:

Uzyc WHERE status = 'completed', ORDER BY imported_at DESC, id DESC i LIMIT 1.

Pytanie:

Jak dziala INSERT w CoreLabTech?

Odpowiedz:

INSERT tworzy nowe rekordy, np. wpis importu w csv_imports albo wiele rekordow

pomiarowych w csv_data. Dla wielu rekordow projekt uzywa bulk insert.

Pytanie:

Po co UPDATE?

Odpowiedz:

UPDATE zmienia istniejacy rekord, np. ustawia status importu na completed,

zapisuje records_saved i error_message.

Pytanie:

Jak dziala DELETE?

Odpowiedz:

DELETE usuwa rekordy. W projekcie trzeba uwazac na dane powiazane: sesje,

fit_data, csv_data, merged_data i ai_results.

Pytanie:

Czym jest INNER JOIN?

Odpowiedz:

INNER JOIN zwraca tylko rekordy, ktore maja dopasowanie w obu tabelach.

Pytanie:

Czym jest LEFT JOIN?

Odpowiedz:

LEFT JOIN zwraca wszystkie rekordy z lewej tabeli oraz dopasowania z prawej,

jesli istnieja. Przydaje sie, gdy chcemy zobaczyc sesje nawet bez analizy.

Pytanie:

Po co GROUP BY?

Odpowiedz:

GROUP BY grupuje rekordy, np. zeby policzyc liczbe pomiarow dla kazdej sesji.

Pytanie:

Dlaczego constraints sa wazne?

Odpowiedz:

Constraints pilnuja integralnosci danych. Primary key identyfikuje rekord,

foreign key pilnuje relacji, UNIQUE blokuje duplikaty, a CHECK moze pilnowac

dozwolonych statusow.

Pytanie:

Jak sprawdzic wolne zapytanie?

Odpowiedz:

Uzyc EXPLAIN ANALYZE, sprawdzic plan wykonania, indeksy, liczbe skanowanych

rekordow i czas wykonania.

Pytanie:

Jak projekt chroni sie przed SQL injection?

Odpowiedz:

Uzywa parametryzowanych zapytan z placeholderami %s. Dynamiczne nazwy tabel sa

dozwolone tylko po walidacji przez allowlist.

34.2 HTTP, auth, cookies i CORS - tlumaczenie PL

Pytanie:

Co to jest HTTP w kontekscie CoreLabTech?

Odpowiedz:

HTTP to protokol komunikacji frontendu z backendem Flask. Aplikacja wystawia

Pytanie:

Jaka jest roznica miedzy GET i POST?

Odpowiedz:

GET pobiera dane i nie powinien zmieniac stanu systemu. POST tworzy dane albo

uruchamia operacje, np. upload, merge albo analysis.

Pytanie:

Co to jest multipart/form-data?

Odpowiedz:

To typ requestu uzywany do uploadu plikow. CoreLabTech uzywa go dla FIT i CSV,

bo request zawiera plik oraz pola formularza, np. session_id.

Pytanie:

Dlaczego Content-Type ma znaczenie?

Odpowiedz:

Backend musi wiedziec, jak sparsowac request. JSON wymaga application/json,

Co to jest CORS?

innej domenie.

Pytanie:

Co to jest idempotency?

Odpowiedz:

Operacja idempotentna daje ten sam efekt przy powtorzeniu. Upload w CoreLabTech

jest czesciowo idempotentny dzieki UNIQUE(session_id, file_hash).

Pytanie:

35.3 Agile testing techniques

35.5 ISTQB Test Analyst

Pytanie:

Jaka jest rola Test Analyst?

Odpowiedz:

Test Analyst analizuje wymagania, projektuje przypadki testowe, dobiera techniki

ocenę jakosci z perspektywy biznesowej/uzytkownika.

Testowanie wartosci granicznych, bo bledy czesto wystepuja na granicach zakresow.

Tabela decyzyjna laczy warunki i akcje. Jest dobra, gdy logika zalezy od wielu

35.6 ISTQB Agile Tester / Advanced Agile Tester

Pytanie:

Co odroznia testowanie Agile od klasycznego?

Odpowiedz:

Pytanie:

Co to whole-team approach?

Odpowiedz:

Pytanie:

Co to test-first?

Odpowiedz:

Przyklady: TDD, BDD, ATDD, example mapping.

Pytanie:

Odpowiedz:

Behavior-Driven Development opisuje zachowanie systemu jezykiem biznesowym,

czesto w formacie Given-When-Then.

Przyklad:

Given a logged-in researcher

When the researcher uploads a valid CSV file

Then the system stores the import and returns csv_saved

Pytanie:

Co to test smells?

Odpowiedz:

Test smells to symptomy slabej jakosci testow, np. flaky tests, zbyt duzo

sleepow, zaleznosc od kolejnosci, duplikacja selectorow, brak danych testowych,

Odpowiedz:

Mob testing to wspolne testowanie przez kilka osob przy jednym problemie.

35.8 Selenium WebDriver

Pytanie:

Co to Selenium WebDriver?

Odpowiedz:

Selenium WebDriver to narzedzie do automatyzacji przegladarek. Pozwala otwierac

strony, wyszukiwac elementy, klikac, wpisywac dane i sprawdzac zachowanie UI.

Pytanie:

Co to Page Object Model w Selenium?

Odpowiedz:

To wzorzec, w ktorym kazda strona ma klase z locatorami i metodami biznesowymi.

Testy nie powinny duplikowac selectorow.

Pytanie:

Jaka jest roznica miedzy implicit wait i explicit wait?

Odpowiedz:

Implicit wait ustawia globalny czas czekania na element. Explicit wait czeka na

konkretny warunek, np. visibilityOfElementLocated. W praktyce explicit wait daje

wieksza kontrole i mniej flaky testow.

Pytanie:

Jak ograniczyc flaky tests w Selenium?

Odpowiedz:

Uzywac explicit waits, stabilnych locatorow, Page Object Model, izolowanych

danych testowych, unikac Thread.sleep i sprawdzac stan biznesowy aplikacji.

Przyklad Java Selenium:

WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));

WebElement button = wait.until(

ExpectedConditions.elementToBeClickable(By.id("submit"))

);

button.click();

35.10 Karate API testing

Odpowiedz:

35.11 Selenium vs Playwright vs Karate vs Rest Assured

Selenium:

UI automation, szerokie wsparcie przegladarek i jezykow, popularne w enterprise.

Playwright:

Nowoczesne UI/E2E, auto-waiting, trace, video, screenshoty, dobre dla stabilnych

testow frontendowych.

Rest Assured:

Java library do REST API, dobre dla technicznych testow API w ekosystemie Java.

Karate:

BDD-like API testing, szybkie kontrakty, czytelne scenariusze, mniej boilerplate.

Jak odpowiedziec na rozmowie:

"Do UI wybralbym Playwright albo Selenium w zaleznosci od stacku firmy. Do API

w Javie uzylbym Rest Assured, a gdy zespol chce czytelne scenariusze

Gherkin-like i szybkie kontrakty, Karate. W CoreLabTech Playwright pasuje do E2E,

Gatling do performance, a Rest Assured/Karate moglyby uzupelnic API contract

testing."

35.13 Ready interview answers EN

Question:

How do you work as a tester in Agile?

Answer:

I participate early in refinement, help define acceptance criteria, identify

risks, prepare examples, automate regression checks, perform exploratory testing

and support the team in meeting the Definition of Done.

Question:

How would you design a test strategy as a Test Manager?

Answer:

I would start with business risks, quality goals and release scope. Then I would

define test levels, test types, environments, data, resources, entry and exit

criteria, metrics and reporting. I would prioritize testing based on risk and

provide transparent go/no-go recommendations.

Question:

How would you test REST APIs in Java?

Answer:

I would use Rest Assured with JUnit or TestNG. I would verify status codes,

headers, JSON schema, required fields, negative cases, authorization and

response times. For readable BDD-like API scenarios, Karate would also be a good

option.

Question:

How would you reduce flaky Selenium tests?

Answer:

I would use explicit waits, stable locators, Page Object Model, isolated test

data, avoid Thread.sleep, keep tests independent and assert business-visible

states rather than implementation details.

36.1 Senior QA - definicja jakosci

Pytanie:

What is software quality?

Odpowiedz PL:

Jakosc oprogramowania to stopien, w jakim system spelnia wymagania biznesowe

i oczekiwania uzytkownika, a jednoczesnie pozostaje niezawodny, bezpieczny,

wydajny i latwy w utrzymaniu. Jakosc to nie tylko brak bugow. Aplikacja moze

nie miec widocznych bledow, ale jezeli nie realizuje celu biznesowego, nie jest

jakosciowa.

Answer EN:

Software quality is the degree to which a system satisfies business

requirements and user expectations while remaining reliable, secure,

performant and maintainable. Quality is not only the absence of defects. If the

software does not solve the business problem, it is not high-quality software.

CoreLabTech example:

System moze poprawnie zapisac plik CSV, ale jezeli merge FIT + CSV tworzy

niepoprawna os czasu albo nie pokazuje wyniku badaczowi, jakosc procesu nadal

jest niewystarczajaca.

36.2 QA vs QC vs Testing

QA:

Quality Assurance dotyczy procesu. QA pyta: jak zaprojektowac proces, aby bledy

powstawaly rzadziej?

QC:

Quality Control dotyczy produktu. QC pyta: czy aktualny produkt ma defekty?

Testing:

Testowanie jest czescia QC. Polega na statycznej lub dynamicznej weryfikacji

produktu, danych, API, UI, konfiguracji i integracji.

Gotowa odpowiedz EN:

QA focuses on improving the process, QC focuses on evaluating the product, and

testing is one of the main QC activities. In practice, a Senior QA should do

more than execute tests: they should prevent defects by improving requirements,

testability, architecture, automation and feedback loops.

36.3 Verification vs Validation

Verification:

Czy budujemy produkt zgodnie ze specyfikacja?

Validation:

Czy budujemy produkt, ktorego naprawde potrzebuje uzytkownik?

CoreLabTech example:

Verification: endpoint /api/sessions zwraca JSON zgodny z kontraktem.

Validation: badacz moze szybko znalezc sesje, uruchomic analize i zrozumiec

wynik.

Interview answer EN:

Verification checks whether we build the product correctly according to

requirements. Validation checks whether we build the right product for the user.

Both are needed, because a technically correct feature can still fail to solve

the user's problem.

36.4 Test levels and test types - odpowiedz Senior

Test levels:

Unit tests: parsery, walidatory, funkcje liczenia cech.

Integration tests: import CSV/FIT + zapis do bazy.

API tests: kontrakty endpointow i przypadki negatywne.

System tests: pelny pipeline w srodowisku z PostgreSQL.

Acceptance/E2E tests: przeplyw uzytkownika w Playwright.

Test types:

Functional: czy funkcja dziala.

Regression: czy poprawki nie zepsuly istniejacych flow.

Smoke: czy aplikacja nadaje sie do dalszego testowania.

Sanity: czy konkretna poprawka dziala.

Exploratory: szybkie wykrywanie ryzyk, ktorych nie ma w checklistach.

Performance: czas importu, merge, analiza, p95/p99.

Security: upload validation, auth, role, CSRF, rate limiting.

Accessibility: semantyka UI, labels, role, kontrast, obsluga klawiatury.

CoreLabTech mapping:

Najwazniejsze sa testy API i integracyjne dla backendu oraz kilka stabilnych

E2E dla krytycznej sciezki: login -> subject -> session -> upload -> merge ->

analysis -> dashboard.

36.5 Risk Based Testing

Definicja:

Risk Based Testing oznacza dobieranie zakresu testow na podstawie ryzyka:

prawdopodobienstwa awarii i jej wplywu na biznes.

Senior answer PL:

Nie testuje wszystkiego tak samo. Najpierw identyfikuje obszary krytyczne:

dane, pieniadze, bezpieczenstwo, integracje, migracje, upload plikow i procesy,

ktore uzytkownik wykonuje najczesciej. Potem dobieram poziom testow: unit, API,

integration, E2E, performance albo exploratory.

Senior answer EN:

I prioritize testing based on risk: business impact, probability of failure,

technical complexity, recent changes and defect history. I do not run all tests

with the same priority. I focus first on critical paths, integrations, security,

data integrity and areas changed recently.

Scenario:

Masz 800 testow i 1 godzine przed releasem. Co robisz?

Odpowiedz:

Uruchamiam smoke, krytyczne testy API, testy zmienionych obszarow, testy

wysokiego ryzyka i najkrotsze E2E potwierdzajace glowne flow. Pelna regresja

idzie nightly albo przed wiekszym release, jezeli czas na to pozwala.

36.6 Defect management

Dobry bug report:

tytul opisujacy problem i obszar,

srodowisko,

wersja/build,

dane testowe,

kroki reprodukcji,

actual result,

expected result,

logi, screenshoty, trace, request/response,

severity i priority,

wplyw biznesowy.

Severity vs Priority:

Severity opisuje techniczny lub biznesowy wplyw defektu. Priority opisuje,

jak szybko zespol powinien go naprawic.

CoreLabTech example:

Defekt: /api/subjects zwraca HTML zamiast JSON.

Severity: High, bo frontend nie potrafi przetworzyc odpowiedzi.

Priority: High, jezeli blokuje demo albo krytyczny flow tworzenia sesji.

Root Cause Analysis:

Po naprawie warto ustalic, dlaczego blad powstal: brak testu kontraktu API,

brak standardowego JSON error handlera, zly endpoint w fetch albo niespojny

url_for w template.

36.10 Page Object Model, fixtures i service layer w testach

Dobry framework Playwright:

Co powinno byc w Page Object:

locatory,

Czego nie dawac do Page Object:

pelnych scenariuszy testowych,

zlozonej logiki biznesowej,

tworzenia danych testowych,

operacji niezwiązanych z dana strona,

asercji, ktore naleza do testu, jezeli ukrywaja intencje scenariusza.

36.13 Playwright vs Selenium - odpowiedz dojrzala

Odpowiedz PL:

Selenium jest dojrzale, szeroko uzywane i ma duzy ekosystem. Playwright jest

nowoczesniejszy dla nowych aplikacji webowych, ma auto-waiting, trace viewer,

latwa rownoleglosc, testy API i dobra obsluge Chromium, Firefox oraz WebKit.

Nie powiedzialbym, ze Selenium jest zle. Wybor zalezy od stacku, kompetencji

zespolu, istniejacego frameworka i potrzeb projektu.

Answer EN:

Selenium is mature, widely adopted and has a large ecosystem. Playwright is a

more modern choice for many new web applications because it provides auto-waiting,

trace viewer, parallel execution, API testing and strong support for Chromium,

Firefox and WebKit. I would not say Selenium is bad. The choice depends on the

project stack, existing framework, team skills and business needs.

36.14 Najtrudniejsze pytania Senior - krotkie odpowiedzi

Pytanie:

How would you design a framework for 10,000 tests?

Answer:

I would split tests by layers, risk and ownership. I would keep most checks at

unit/API level, limit E2E to critical flows, run tests in parallel, use stable

fixtures, isolate test data, collect trends and remove flaky tests aggressively.

Pytanie:

How would you reduce regression time from 5 hours to 30 minutes?

Answer:

I would analyze test duration and value, split smoke from full regression,

parallelize execution, move logic checks from UI to API, remove duplicates,

stabilize data setup and run long suites nightly instead of on every commit.

Pytanie:

How do you improve an existing automation framework?

Answer:

First I audit failures, duplication, flaky tests, test data, locators,

reporting and CI time. Then I improve the highest-impact areas incrementally:

stable selectors, better fixtures, API data setup, clearer layers, useful

reports and quality gates.

Pytanie:

How do you convince a team to automate?

Answer:

I focus on business value: faster feedback, lower regression cost, fewer

production defects and more confidence during releases. I start with a small,

stable smoke suite that proves value quickly.

Robot Framework Interview Prep / Przygotowanie do rozmowy

Why this matters / Dlaczego to wazne

EN: Robot Framework is a keyword-driven test automation framework often used for acceptance testing, regression testing, API testing, and end-to-end checks. It is especially useful when QA, developers, and business stakeholders need readable tests that describe behavior in a shared language.

PL: Robot Framework to framework automatyzacji testow oparty na slowach kluczowych. Czesto uzywa sie go do testow akceptacyjnych, regresji, API oraz testow end-to-end. Jest przydatny, gdy QA, developerzy i biznes chca czytelnych testow opisujacych zachowanie systemu wspolnym jezykiem.

Core concepts / Kluczowe pojecia

EN: Test suite - a .robot file or directory containing tests. Test case - one scenario. Keyword - reusable action or assertion. Library - Python/Java/.NET or built-in extension that exposes keywords. Resource file - shared keywords, variables, and imports. Variables - scalar ${name}, list @{items}, dictionary &{data}. Tags - labels used for selection, reporting, and CI filtering.

PL: Suite testowy to plik .robot albo katalog z testami. Test case to pojedynczy scenariusz. Keyword to wielokrotnego uzytku akcja lub asercja. Library dostarcza slowa kluczowe, np. SeleniumLibrary, RequestsLibrary albo wlasna biblioteka Python. Resource file przechowuje wspolne keywordy, zmienne i importy. Zmienne moga byc skalarne ${name}, listowe @{items} i slownikowe &{data}. Tagi pomagaja wybierac testy, raportowac i filtrowac uruchomienia w CI.

Minimal test example / Minimalny przyklad testu

*** Settings ***

Library SeleniumLibrary

Resource resources/common_keywords.robot

*** Variables ***

${BASE_URL} https://example.test

*** Test Cases ***

User Can Log In With Valid Credentials

[Tags] smoke login

Open Browser ${BASE_URL}/login chrome

Input Text id=username qa_user

Input Password id=password correct-password

Click Button css=button[type="submit"]

Page Should Contain Dashboard

[Teardown] Close Browser

EN: The example shows Settings, Variables, Test Cases, tags, reusable imports, SeleniumLibrary keywords, assertions, and teardown.

PL: Przyklad pokazuje sekcje Settings, Variables, Test Cases, tagi, importy wielokrotnego uzytku, keywordy SeleniumLibrary, asercje i teardown.

API test example / Przyklad testu API

*** Settings ***

Library RequestsLibrary

Library Collections

*** Test Cases ***

Get User Returns 200 And Expected Email

Create Session api https://reqres.in/api

${response}= GET On Session api /users/2

Status Should Be 200 ${response}

${json}= Set Variable ${response.json()}

Dictionary Should Contain Key ${json} data

Should Be Equal ${json}[data][email] janet.weaver@reqres.in

EN: In interviews, explain that API tests should verify status codes, schema or key fields, business values, error cases, authentication, and contract stability.

PL: Na rozmowie warto powiedziec, ze testy API powinny sprawdzac statusy HTTP, schemat lub kluczowe pola, wartosci biznesowe, przypadki bledow, autoryzacje i stabilnosc kontraktu.

Interview questions and answers / Pytania i odpowiedzi rekrutacyjne

Q1 EN: What is Robot Framework and when would you use it?

A1 EN: It is a generic, keyword-driven automation framework. I would use it for acceptance, regression, smoke, API, and end-to-end tests where readable test scenarios and reusable keywords are important.

P1 PL: Czym jest Robot Framework i kiedy go uzyjesz?

O1 PL: To ogolny framework automatyzacji oparty na slowach kluczowych. Uzyje go do testow akceptacyjnych, regresyjnych, smoke, API i end-to-end, gdy wazna jest czytelnosc scenariuszy oraz ponowne uzycie keywordow.

Q2 EN: What is the difference between a test case and a keyword?

A2 EN: A test case describes the scenario and expected behavior. A keyword is a reusable step that performs an action or assertion. Good suites keep test cases readable and move technical details into keywords.

P2 PL: Jaka jest roznica miedzy test case a keywordem?

O2 PL: Test case opisuje scenariusz i oczekiwane zachowanie. Keyword to wielokrotnie uzywany krok wykonujacy akcje albo asercje. Dobre suite utrzymuja testy czytelne, a detale techniczne przenosza do keywordow.

Q3 EN: How do you structure a maintainable Robot Framework project?

A3 EN: I separate tests, resources, page/object or API keywords, variables, and test data. I keep low-level selectors in one place, use tags for execution scope, avoid duplicated steps, and run tests through CI with reports and logs archived.

P3 PL: Jak zorganizujesz utrzymywalny projekt Robot Framework?

O3 PL: Oddzielam testy, resource files, keywordy dla stron lub API, zmienne i dane testowe. Selektory trzymam w jednym miejscu, tagami kontroluje zakres uruchomien, unikam duplikacji i uruchamiam testy w CI z archiwizacja raportow oraz logow.

Q4 EN: How do variables work in Robot Framework?

A4 EN: Scalars use ${name}, lists use @{items}, and dictionaries use &{data}. Variables can be defined in the Variables section, resource files, variable files, command line options, or returned from keywords.

P4 PL: Jak dzialaja zmienne w Robot Framework?

O4 PL: Skalary maja forme ${name}, listy @{items}, a slowniki &{data}. Zmienne mozna definiowac w sekcji Variables, plikach resource, plikach zmiennych, parametrach linii komend albo zwracac z keywordow.

Q5 EN: What is the role of tags?

A5 EN: Tags categorize tests and let us include or exclude groups such as smoke, regression, api, ui, critical, or flaky. In CI, tags help run fast checks on pull requests and broader suites nightly.

P5 PL: Po co sa tagi?

O5 PL: Tagi kategoryzuja testy i pozwalaja wlaczac albo wykluczac grupy, np. smoke, regression, api, ui, critical lub flaky. W CI tagi pomagaja uruchamiac szybkie testy dla pull requestow i pelne suite w nocy.

Q6 EN: How do you handle setup and teardown?

A6 EN: Robot supports suite, test, and keyword setup/teardown. I use them to prepare preconditions and clean up state, for example opening and closing browser sessions, resetting test data, or removing created records.

P6 PL: Jak obslugujesz setup i teardown?

O6 PL: Robot wspiera setup i teardown na poziomie suite, testu i keywordu. Uzywam ich do przygotowania warunkow oraz sprzatania stanu, np. otwarcia i zamkniecia przegladarki, resetu danych testowych lub usuniecia utworzonych rekordow.

Q7 EN: How would you reduce flaky UI tests?

A7 EN: I avoid fixed sleeps, use explicit waits, stable selectors, isolated test data, short independent scenarios, screenshots/logs on failure, and I move checks to API level when UI coverage is not necessary.

P7 PL: Jak ograniczysz niestabilne testy UI?

O7 PL: Unikam sztywnych sleepow, stosuje explicit waits, stabilne selektory, izolowane dane testowe, krotkie niezalezne scenariusze, screenshoty i logi przy bledach oraz przenosze czesc sprawdzen na poziom API, gdy UI nie jest potrzebne.

Q8 EN: How do you integrate Robot Framework with CI/CD?

A8 EN: I install dependencies, run robot with selected tags, publish output.xml, log.html and report.html as artifacts, fail the pipeline on critical failures, and optionally merge results with rebot.

P8 PL: Jak zintegrujesz Robot Framework z CI/CD?

O8 PL: Instaluje zaleznosci, uruchamiam robot z wybranymi tagami, publikuje output.xml, log.html i report.html jako artefakty, oblewam pipeline przy krytycznych bledach i opcjonalnie lacze wyniki narzedziem rebot.

Useful commands / Przydatne komendy

robot tests/

robot --include smoke --outputdir results tests/

robot --exclude flaky tests/

robot --variable BASE_URL:https://staging.example.com tests/

rebot --merge output-*.xml

EN: Be ready to explain the generated files: output.xml is the machine-readable result, log.html is detailed execution evidence, and report.html is the summary for humans.

PL: Przygotuj sie do wyjasnienia plikow wynikowych: output.xml to wynik maszynowy, log.html zawiera szczegolowy przebieg wykonania, a report.html jest podsumowaniem dla ludzi.
